USB Protocols & Serial Communications

USB looks like a cable and a connector. Underneath, it is a layered bus protocol with enumeration, descriptors, endpoints, transfer types and host scheduling. Serial communications are the useful counterpoint: much simpler, much older, and still everywhere.

The first mental model: USB is not just “serial over a cable”

USB moves bits serially, but architecturally it is very different from a classic UART link. A UART normally gives two peers a byte stream with agreed settings such as baud rate, data bits and parity. USB is host-controlled: the host discovers devices, assigns addresses and initiates bus transactions.

That distinction explains a lot of USB behaviour. A device exposes endpoints and the host schedules transfers to them rather than treating the bus as an unconstrained byte stream.

USB's layers

  • Physical layer: signalling, electrical characteristics, connectors and link speed.
  • Protocol layer: packets, addresses, endpoints, transfers, handshakes and error detection.
  • Device model: descriptors describe the device, configurations, interfaces and endpoints.
  • Host software: the OS maps USB interfaces to class drivers or vendor drivers.
  • Application: programs normally use an OS abstraction rather than manipulating USB signalling directly.

Enumeration: how the host discovers a device

Plug in a USB device and the operating system appears to know what it is. That process is enumeration.

  1. The host detects a new device on a port.
  2. The device initially responds at the default USB address.
  3. The host retrieves descriptors.
  4. The host assigns a unique address.
  5. The host selects a configuration.
  6. The OS identifies interfaces and loads appropriate drivers.

Descriptors are effectively the device's machine-readable introduction. They include things such as vendor/product identifiers, configurations, interfaces and endpoint definitions.

Debugging insight: “The device is visible but my application cannot use it” often means enumeration succeeded but the expected interface, driver, permissions or endpoint setup did not.

Endpoints are the real USB abstraction

A USB device exposes one or more endpoints. Think of an endpoint as a typed communication mailbox. Endpoint zero is special: every USB device has it and it is used for control transfers, including enumeration.

Other endpoints are associated with interfaces and carry application data. Endpoint direction is expressed from the host's perspective: IN means device → host and OUT means host → device.

The name interrupt transfer is a common source of confusion. It does not mean the USB device raises a CPU interrupt. The host schedules the endpoint according to the USB protocol.

USB CDC: when USB becomes a serial port

USB can emulate a traditional serial port through the CDC device class, commonly CDC ACM. This is why a microcontroller can appear as something like /dev/ttyACM0 on Linux or a COM port on Windows.

The physical transport is USB while the application-facing abstraction is serial. The OS driver translates between the two.

Classic UART serial: deliberately simple

A UART normally has no concept of devices, enumeration or endpoints. It serialises bytes using an agreed framing format.

idle | start | data bits | optional parity | stop | idle

        <----------- one character ---------->

A common configuration is 115200 8N1: 115200 symbols per second, 8 data bits, no parity and one stop bit. The sender and receiver must agree on the framing parameters.

UART is asynchronous: there is no shared clock wire. The receiver estimates bit timing from the configured baud rate and the start bit.

RS-232, TTL UART and RS-485 are not the same thing

“Serial” describes a communication style, not one electrical standard.

  • TTL UART: logic-level signals used inside embedded systems and development boards.
  • RS-232: a different electrical interface with different voltage conventions and signalling rules.
  • RS-485: differential signalling designed for robust multi-device buses and longer cable runs.

A USB-to-UART adapter and a USB-to-RS-232 adapter may look similar from the computer's point of view while being electrically incompatible on the far side.

Baud rate is not automatically bytes per second

For simple binary UART, baud and bits per second are often treated as equivalent. Application throughput is lower because each character includes framing overhead.

115200 baud ÷ 10 bits/byte ≈ 11,520 bytes/second

With 8N1, one byte normally occupies 10 bits: one start bit, eight data bits and one stop bit. Application protocols may add their own framing, checksums and acknowledgements.

Where the interesting bugs live

Framing mismatches

UART problems often begin with a tiny mismatch: 9600 8N1 on one side and 9600 7E1 on the other. The wire is active, but the bytes are garbage.

Assuming writes equal messages

Neither UART nor many USB serial APIs guarantee that one application write corresponds to one application read. If your protocol sends messages, define framing yourself.

[SYNC][LENGTH][TYPE][PAYLOAD...][CRC]

A robust receiver can maintain a state machine: find sync, read the header, collect the declared payload, verify the CRC, emit a message and recover if corruption occurs.

Blocking reads

A serial device may deliver one byte now and the rest later. Production code treats I/O as incremental and asynchronous rather than assuming a complete message arrives in one read.

Permissions and drivers

Hardware visibility, driver binding and application permissions are separate concerns. “The OS sees the USB device” does not imply that an arbitrary application can open its interface.

A useful experiment

Connect two serial endpoints, or a development board and a USB serial adapter. Send a deliberately fragmented message one character at a time with random delays. Then build a receiver that buffers bytes and parses complete messages.

[SYNC] [LENGTH] [TYPE] [PAYLOAD] [CRC]

0xAA     0x0B     0x02    ...       0x7C

Add a timeout, a maximum message length and CRC validation. This small experiment makes the difference between a byte stream and a real application protocol very obvious.

The bigger connection

USB and UART illustrate a general systems principle: separate transport from protocol. A byte stream is not a message protocol. A USB endpoint is not an application API. TCP is not HTTP. Ethernet is not IP.

Once you see these as layers, many systems become easier to reason about. Each layer provides guarantees to the layer above it, while deliberately leaving other guarantees to a higher layer.

Takeaway: USB gives you a sophisticated host-controlled transport and device model. UART gives you a minimal byte-level mechanism. In both cases, reliable application software comes from understanding exactly where framing, flow control, errors and message boundaries are — and where they are not.
